# Operations and troubleshooting

## Configuration

Configuration is read once at process startup. Restart after rotating credentials. Secrets are checked when their service is called, so the server can initialize without keys.

| Variable | Default | Purpose |
|---|---|---|
| `GRONA_API_KEY` | unset | Embed workspace secret, generated by an Owner/Admin in Settings → Secrets. |
| `GRONA_MOBILE_API_KEY` | unset | Separate mobile grants secret supplied by Grona. No fallback to the Embed key. |
| `GRONA_BASE_URL` | `https://services.grona.ai/api/public/v1` | Embed base URL. Change only for a trusted test/service deployment. |
| `GRONA_MOBILE_BASE_URL` | `https://api.grona.ai` | Mobile origin; `/v1/mobile/grants` is appended. |
| `GRONA_AUTH_MODE` | `bearer` | Embed authentication: `bearer` → `Authorization: Bearer …`; `header` → `X-API-Key: …`. Mobile always uses Bearer. |
| `GRONA_TIMEOUT_MS` | `30000` | Timeout per ordinary HTTP attempt, including response body reading. |
| `GRONA_VERIFY_TIMEOUT_MS` | `90000` | Timeout per snippet-check attempt; verification can take several seconds. |
| `GRONA_MAX_RETRIES` | `2` | Additional attempts for operations that can safely be replayed. `0` disables automatic retry. |
| `GRONA_MAX_RETRY_DELAY_MS` | `60000` | Maximum automatic wait. A server-requested longer delay is returned to the caller instead of retrying early. |

Use the MCP client's environment configuration or Node `--env-file=.env`. The library itself does not search for `.env` files. Blank keys count as unconfigured. Invalid configuration fails startup with a concise diagnostic on stderr. Never include a secret in a base URL.

`grona_configuration` reports service configuration without revealing credential contents. It does not test key validity or entitlements. A configured key can still be revoked or unauthorized.

## Response and error handling

A successful direct tool returns the original Grona `{ "data": …, "meta": … }` envelope as JSON text and MCP `structuredContent`. Extra fields and future response enum values survive. `meta.workspaceId` is resolved by Grona from the relevant credential. Lists have `meta.count`; v1 returns the complete list without pagination or a defined order.

Tool execution failures use MCP `isError: true` and a machine-readable error object. Branch on stable `error.code` and HTTP status, rather than parsing human wording. Schema/protocol validation may be rejected by the SDK before tool execution. Reference resources and prompts contain no credentials.

| HTTP / condition | Grona code | Recovery |
|---|---|---|
| 400 | `invalid_request` | Correct input. No mutation was applied. Check required fields and campaign type/targeting restrictions. |
| 401 | `unauthorized` | Check the key for this service; rotate/reconfigure if revoked. |
| 403 | `forbidden` | Check workspace plan/feature limits and access. Failed create creates nothing. |
| 404 | `not_found` | Re-read campaign/variation ids; verify the workspace. Unknown API paths also return 404. |
| 409 | `conflict` | `externalId` already belongs to a campaign. Fetch and compare identity before recovery. |
| 429 | `rate_limited` | Respect `Retry-After`; fixed rate limits are not published. |
| 500 / gateway 5xx | `internal` or gateway failure | Retry only if the operation is safe. Gateway bodies may be text rather than an API envelope. |
| Mobile 503 | service unavailable | Honor `Retry-After` where supplied; retry the same customer's fetch. |
| Network/timeout | local client error | Outcome of a mutation may be unknown. Recover a create through `externalId`; inspect updates/deletes by immutable Grona id before taking further action. |
| Missing credential | local configuration error | Set the corresponding environment key and restart. Local helpers remain available. |

The client sanitizes sensitive values in failure messages and never logs request/response bodies. Treat successful tool outputs as sensitive where they include editor links, previews or grants; MCP clients may retain conversation/tool history.

## Retry policy

Reads, editor-link operations, script verification and mobile grant fetches can be retried. Create is automatically replayed only when an `externalId` makes duplication impossible. `grona_create_campaign_once` handles a conflicting create by fetching the existing campaign and checking its identity before returning it.

PATCH and DELETE are not automatically replayed by the client. In particular, an `externalId` can be changed, cleared or reused after deletion. If an agent retries a mutation manually, it must first record and then use Grona's immutable campaign `id`, never the external id. A repeated delete by immutable id can return 404 after the first delete succeeded; establish that prior attempt before treating the absence as success. An initial 404 remains a failure.

`Retry-After` accepts seconds and, for mobile, an HTTP date. Automatic retries respect the header. Ordinary retryable failures use bounded exponential backoff and jitter. A delay beyond the configured wait limit is surfaced for later retry instead of shortening the upstream wait. Each retry has its own timeout; total wall time can exceed one timeout. There is no upstream `Idempotency-Key` header.

Do not assume a 409 proves equality with the intended create. In particular, specific campaigns omit their original URL on get/list; preview URLs can help identify the page, but campaigns with missing variations may be impossible to compare safely. The create-once helper fails on ambiguous/mismatched identity rather than modifying an existing campaign.

## Workspace and link access

One Embed key selects one workspace. Grona's key has workspace-wide access and cannot enforce end-user campaign ownership. Treat this MCP server as a trusted workspace tool. Use separate workspaces and separate server instances when users must be isolated.

Editor links grant editor access to whoever holds them. They expire 15 minutes after `generatedAt`. Validate a held link before opening it and always use the returned `data.editUrl`, even if `valid` is false: Grona may have refreshed it. Grona refreshes links close to expiry, approximately two minutes remaining. Open links promptly; avoid storing or forwarding them. There is no API to revoke an individual editor link early. Preview URLs also expose a variation to anyone holding the URL.

The server returns requested links because that is the API's purpose; it cannot prevent an MCP client from retaining successful responses. Do not paste live links or grants into public chat, tickets, logs or analytics. The server does not open browsers automatically.

## Installation and launch checks

Install the **Grona Embed** snippet from the Embed dashboard into `<head>` on every targeted page. The Website product's `cdn.grona.ai` script is a different integration. Set the page variable before the Embed snippet where possible. Snippet generation is a convenience; copy the dashboard version when the workspace enables anti-flicker, because the API exposes no anti-flicker configuration.

A verification result of `present` means the workspace snippet was found on one page. It does not establish that the script executes, consent allows it, CSP permits it, anti-flicker exists, or the campaign has been edited or previewed. `absent` also covers pages that Grona cannot load. Login walls, bot protection, delayed tag-manager installation, optimization plugins and consent tools can cause an apparent absence.

Campaign `script.status` is a stored background check and can be `checking`, `present`, `absent` or `unknown`; `checkedAt` can be null. Launch readiness uses a fresh explicit verification call for a page associated with the campaign. Changes to campaign status or deletion can take time to reach visitors.

CSP must allow at least `https://personalize.grona.ai` and `https://services.grona.ai`; Grona documents an inline style requirement in `style-src`. Evaluate the exact policy and any additional variation asset origins for your site. [Grona installation guide](https://developer.grona.ai/api/install-the-snippet/).

## Mobile grants

`grona_issue_grants` calls only `POST https://api.grona.ai/v1/mobile/grants`. Supply `customerId` from the shopper's authenticated server session; the MCP server cannot establish a shopper session on your behalf. It is an opaque 1–128 character id containing letters, digits, `.`, `_`, `:` or `-`, never email, phone or national identity data.

Return grants to the app unchanged. An empty list means no current grant applies. Repeated calls fetch currently valid grants. Do not cache beyond `exp`, share across shoppers, or assume decoding proves authenticity. Your order backend verifies each token and consumes each `jti` once; once-per-customer offers require an additional customer rule. This MCP server does not implement redemption or payment/order authorization: Grona has no redemption endpoint. [Mobile grants API](https://developer.grona.ai/api/mobile-grants/).

## Package and container

The repository can produce an npm tarball without publishing it:

```bash
npm ci
npm run verify
npm pack
```

After installing the tarball, the `grona-mcp` executable starts the stdio server. This project is not automatically published to any registry. Programmatic integration can import the server factory and API client from the package's exports; consult their generated TypeScript declarations.

A Docker build is also supplied:

```bash
docker build -t grona-mcp .
docker run --rm -i --env-file .env grona-mcp
```

Use `-i` to keep stdin open. Do not allocate a TTY or expose an HTTP port: this implementation uses stdio. Run a distinct container/process per trust boundary. The image runs as the unprivileged `node` user. A remote HTTP transport, client OAuth layer and multi-tenant routing are outside this stdio server's implementation.
