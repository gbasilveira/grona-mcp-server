Conventions
These conventions apply to every endpoint of the Public API v1. Read this page once before you build an integration: it covers how ids work, what an absent or
null
field means, and how to retry a request without creating a duplicate.
Requests
Section titled “Requests”
Send requests over HTTPS to
https://services.grona.ai/api/public/v1
. The paths on these pages are relative to it.
Send request bodies as JSON with
Content-Type: application/json
.
Authenticate every call with your workspace secret key. See
Authentication
.
Identifiers
Section titled “Identifiers”
Grona ids for campaigns, variations and workspaces are strings. Treat them as opaque: store them as they are and do not parse them or depend on their length or format.
Wherever a path takes a
campaignId
, you can pass either Grona’s campaign id or your own
externalId
. Grona checks both at once, so you do not have to say which one you sent. If a value happens to match both, Grona’s id wins.
External ids
Section titled “External ids”
An
externalId
is your own id for a campaign, such as the id of the record in your product that created it. Set it on create or on update.
It is optional. A campaign without one reads back as
"externalId": null
.
It is 1 to 128 characters from letters, digits,
_
,
.
,
:
and
-
. A UUID, an ObjectId or a number sent as a string all work.
It is unique within the workspace. Sending one that another campaign already uses returns
409 conflict
, so a lookup by
externalId
always finds exactly one campaign.
Sending a campaign’s own current
externalId
again is fine.
Sending
null
on update removes it and frees it for another campaign. Deleting a campaign frees its
externalId
too.
It comes back on every campaign in every response.
Terminal window
curl
https://services.grona.ai/api/public/v1/campaigns/CMP-1024
\
-H
"Authorization: Bearer
$GRONA_SECRET_KEY

Timestamps
Section titled “Timestamps”
Timestamps are ISO 8601 strings in UTC with millisecond precision, such as
2026-10-20T09:30:12.418Z
. Compare them as instants, not as strings, and use your server clock, not the shopper’s.

Unknown fields and values
Section titled “Unknown fields and values”
v1 can gain fields, endpoints, optional parameters and enum values without a new version. Write clients that ignore fields they do not recognise and that handle an unknown value of
status
,
script.status
,
type
or
error.code
without failing. See
Versioning and deprecation
.
Traffic split keys
Section titled “Traffic split keys”
An A/B test’s
trafficSplit
uses two kinds of key, for one reason: the variation ids do not exist until the campaign does.
On create
, key it by role:
{ "Control": 60, "Test": 40 }
.
On update and in every response
, it is keyed by variation id, with every variation present:
{ "671a3d52e4b0a1f2c3d40022": 60, "671a3d52e4b0a1f2c3d40023": 40 }
.
The values are whole numbers that total 100. Leave
trafficSplit
out on create to split 50 and 50. A
general
campaign has no split, and sending one returns
400
.
Variation types
Section titled “Variation types”
Each variation has a
type
of
control
or
variant
. An A/B test’s two variations, Control and Test, read
control
and
variant
, in that order. A general campaign has one variation and no control, so do not rely on
type
there. A variation whose
name
is
null
reads
variant
.
Lists and pagination
Section titled “Lists and pagination”
List endpoints return every item in one response. v1 has no pagination, and
meta.count
holds the number of items returned. The field is reserved so pagination can be added later without breaking your code.
The order of a list is not specified. If you need an order, sort on your side, for example by
createdAt
.
Rate limits
Section titled “Rate limits”
Grona does not publish fixed rate limits. If you send too many requests you get
429 rate_limited
with a
Retry-After
header. Wait that many seconds, then retry. During a short outage you can get a
5xx
, which you retry with exponential backoff and jitter. See
Errors
.
Safe retries and idempotency
Section titled “Safe retries and idempotency”
The API has no
Idempotency-Key
header. Use
externalId
as the idempotency key for creates instead: because it is unique per workspace, a create that is sent twice cannot make two campaigns.
Send the create with an
externalId
.
If the response is lost or times out, send the same create again.
If the retry returns
409 conflict
, the first attempt succeeded. Fetch the campaign with
GET /campaigns/{externalId}
.
Get and list do not return editor links, so request a fresh link for each variation with
POST /variations/edit-link
.

Retry updates and deletes by Grona’s id
Section titled “Retry updates and deletes by Grona’s id”
When you retry a
PATCH
or a
DELETE
, address the campaign by the Grona
id
returned earlier, not by
externalId
. Deleting a campaign frees its
externalId
for reuse, and an update can change or clear it, so another campaign can take the same
externalId
between your first attempt and the retry. A retry by
externalId
would then change or delete that other campaign, and deletion is permanent. A delete retried by Grona’s
id
returns
404
if the first attempt succeeded; treat that as done.
